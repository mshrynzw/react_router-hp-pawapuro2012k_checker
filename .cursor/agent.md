# パワプロ2012経験値計算アプリ 専用AI開発方針

## アプリ概要

- 本アプリは「実況パワフルプロ野球2012決定版 サクセス」の投手育成における経験値計算を支援する。
- ユーザーが現在能力と目標能力を入力すると、必要な筋力・敏捷・技術・精神ポイントを即時に可視化する。
- 目的は単なる計算機ではなく、育成計画を立てるためのシミュレーション体験を提供すること。

## 世界観

- UI全体は「近未来の育成HUD」を基調にし、ゲーム内育成画面を現代的に再構築する。
- 数値は「データ」ではなく「成長の手触り」として表現し、達成感と戦略性を演出する。
- カジュアルさよりも、洗練・信頼感・没入感を優先する。

## UI/UX方針

- 最優先は「直感的に入力できる」「結果を瞬時に理解できる」「次の行動が明確」の3点。
- 入力UIはタップ/クリック負荷を下げ、育成画面のようにテンポ良く操作できる設計にする。
- 主要情報（不足経験値、差分、優先項目）を視線誘導で上から順に理解できるレイアウトにする。
- アニメーションは控えめにし、反応速度・読みやすさ・操作の気持ちよさを優先する。

## コーディング方針

- すべてTypeScriptで実装し、`any` は禁止。
- 小さく責務が明確な関数/コンポーネントを優先し、読みやすさと保守性を担保する。
- 計算ロジックは純関数として分離し、副作用のある処理をUI層に混在させない。
- 既存実装を壊さず、変更は最小単位かつ意図が追跡可能な形で行う。

## コンポーネント設計

- 関数コンポーネントのみ使用する。
- 1コンポーネント1責務を徹底し、肥大化した場合は表示/ロジック/入力単位で分割する。
- 再利用されるUIは `components/ui` または共通コンポーネントへ集約する。
- 機能固有UIは `features/<domain>` 配下に置き、共通UIと分離する。

## 命名規則

- コンポーネント: `PascalCase`（例: `PitchAbilityCard`）
- 関数・変数: `camelCase`
- 定数: `UPPER_SNAKE_CASE`
- 型・インターフェース・Zod schema名はドメインが分かる接頭辞をつける（例: `PitchAbilityInputSchema`）。
- 真偽値は `is/has/can/should` で始める。

## TypeScript方針

- 型推論を活かしつつ、外部境界（props, form, API, utility戻り値）には明示的な型を付与する。
- `unknown` を適切に絞り込み、型アサーションの乱用を避ける。
- `enum` より union型と `as const` を優先し、データ駆動で扱う。
- ドメイン型（能力・経験値・入力値）は `types` または `features` 配下で管理する。

## Tailwind設計方針

- utility-firstで実装し、重複するクラスは `cn` と共通コンポーネントで集約する。
- 青系グラデーション、ガラスモーフィズム、subtle glowを一貫して使う。
- spacing, radius, shadow, z-index はスケールを統一し、場当たり調整を避ける。
- 状態表現（hover/focus/active/disabled）は全画面でトーンを合わせる。

## shadcn/ui の利用ルール

- フォーム、カード、ダイアログ、トーストなどの基盤UIは shadcn/ui を優先活用する。
- 直接改変は最小限にし、拡張はラッパーコンポーネントで吸収する。
- `className` 上書き時もアクセシビリティ属性とインタラクション挙動を維持する。

## フォーム実装ルール

- フォームは React Hook Form を標準採用する。
- 入力コンポーネントは `FormField` を通し、エラー・説明文・ラベルを一貫表示する。
- 数値入力はキーボード種別、最小/最大、ステップを設計段階で定義する。
- 変更時のフィードバックは即時だが、過度なバリデーション警告は避ける。

## Zodバリデーション方針

- すべてのフォーム入力をZod schemaで検証し、`zodResolver` を使う。
- バリデーションメッセージは日本語で、ユーザーが次に取るべき行動が明確な文言にする。
- 能力値の上下限・相互依存をドメインルールとして schema に集約する。

## レスポンシブ設計

- モバイルファーストで実装する。
- 主要操作は親指で押しやすいサイズ（タップ領域）を確保する。
- スマホでは入力と結果の往復がしやすい縦導線、PCでは比較しやすい2カラムを基本とする。

## 状態管理方針

- 局所状態はコンポーネント内に閉じる。
- 複数コンポーネントで共有する状態のみ、カスタムフックまたはコンテキストへ昇格する。
- 計算可能な値は保存せず導出し、単一情報源を保つ。

## ディレクトリ構成ルール

- `features` を中心に機能単位で分割し、`components` は共通部品のみに限定する。
- `schemas`, `constants`, `types`, `utils` を分離し、依存方向を `ui -> feature -> lib` へ揃える。
- ページルートは React Router v7 に沿って `app/routes` で管理する。

## パフォーマンス方針

- 不要な再レンダリングを防ぐため、props設計とコンポーネント分割を先に見直す。
- 高コスト計算はメモ化または事前計算し、入力中の体感遅延を出さない。
- 大きな定数データはモジュール分割し、描画パスから切り離す。

## アクセシビリティ方針

- すべての入力要素にラベルを紐づける。
- キーボード操作とフォーカス可視性を確保する。
- 色だけに依存しない情報提示（アイコン、文言、数値）を行う。

## 再利用性方針

- 能力入力、差分表示、経験値表示は独立コンポーネント化し、再配置可能にする。
- ドメイン定数（基礎能力・変化球一覧）は単一定義で管理し、重複定義を禁止する。
- UIパターンは再利用前提でAPIを設計し、画面専用の一回きり実装を避ける。

## デザイン原則

- 情報整理を最優先し、視覚効果は読解を補助する範囲に留める。
- コントラスト・余白・整列で「高級感」と「信頼感」を表現する。
- 数値の可読性（桁揃え、強調、単位明示）を最重要視する。

## このアプリ固有の能力仕様

- 基礎能力: 球速, コントロール, スタミナ
- 変化球: スライダー, Hスライダー, カットボール, カーブ, スローカーブ, ドロップ, Dカーブ, スラーブ, フォーク, パーム, SFF, Vスライダー, チェンジアップ, シンカー, Hシンカー, サークルチェンジ, シュート, Hシュート, ツーシーム, 超スローボール, ナックル, ナックルカーブ, オリジナル変化球
- これらはUI・型・バリデーション・計算ロジックで同一の定数ソースを参照すること。

## 禁止事項

- CRUDテンプレート流用の平板なUI実装
- `any` の使用、型安全を崩す実装、暫定的なマジックナンバー放置
- Fat Component（巨大コンポーネント）とロジック直書き
- 可読性を損なう過剰装飾、色の乱用、旧式Bootstrap風デザイン
- エラーハンドリング省略、アクセシビリティ無視、テスト不能な密結合実装

## 最重要原則

- このプロジェクトは「パワプロの育成体験を現代的UIで再構築する」ためのプロダクトである。
- 実装判断に迷った場合は、ユーザーが「能力を伸ばす楽しさ」「育成シミュレーション感」「ステータス管理の快感」を感じられるかを最優先基準とする。
- 常に個人制作の延長ではなく、洗練された実サービス品質を目指す。
